# เอกสารออกแบบ: แอปผู้ช่วย AI บนเดสก์ท็อป (Rust)

วันที่: 2026-11-11
สถานะ: ร่าง รอผู้ใช้อนุมัติ

## 1. เจตนาและเหตุผล

ผู้ใช้ต้องการแอปผู้ช่วย AI บนเดสก์ท็อปที่เป็นของตัวเอง ความสามารถแบบเดียวกับ Grok Bot (แอป Electron ที่แกะดูจาก `Grok_Bot_0.79.4_Setup.exe`) แต่เขียนใหม่ด้วย Rust ใช้ชื่อ แบรนด์ และหน้าตาของตัวเอง

ส่วนที่ต่างจากแอปทั่วไปคือ **Jev** (TypeSafe AI) Jev ไม่ได้ใช้คุยกับผู้ใช้ แต่ทำหน้าที่ **ตัดสินใจ** อยู่เบื้องหลัง ทุกการตัดสินใจมีค่าความน่าจะเป็นและค่าความมั่นใจ แอปใช้ค่าเหล่านี้เลือกว่าจะทำต่อเองหรือถามผู้ใช้ก่อน

## 2. เป้าหมาย

เวอร์ชันแรก (v1):

1. แชตกับ AI แบบข้อความขึ้นทีละส่วน (streaming) เลือกตัวคุยได้ 3 ทาง
   - **Hermes**
   - **Claude CLI** ที่ติดตั้งในเครื่อง
   - **โมเดลผ่าน API key** ที่ผู้ใช้ใส่ในหน้าตั้งค่า
2. **Jev เลือกตัวคุย (routing)**: Jev ตัดสินว่าข้อความแต่ละข้อความควรไปตัวคุยตัวไหน
3. **Agent รันคำสั่งบนเครื่อง**: AI เสนอคำสั่ง shell ได้ แล้วแอปรันให้
4. **Jev ตรวจคำสั่งก่อนรัน**: Jev ตัดสินว่าคำสั่งปลอดภัยหรือไม่ ถ้าไม่แน่ใจต้องถามผู้ใช้ก่อน
5. เก็บประวัติแชตไว้ในเครื่อง
6. Export บทสนทนาเป็นไฟล์

## 3. สิ่งที่ไม่ทำใน v1

- Connector ไปบริการภายนอก (Reddit, MCP servers และอื่น ๆ)
- ตัวจัดการรหัสผ่าน และ import จาก Bitwarden/1Password/เบราว์เซอร์
- จับภาพหน้าจอ อ่านข้อความบนบัตร ค้นหาที่อยู่ WebAuthn
- รองรับ macOS/Linux (v1 รองรับ Windows อย่างเดียว)
- ระบบอัปเดตอัตโนมัติ ตัวติดตั้ง และการ sign code

ทั้งหมดนี้เป็นงานถัดไป แต่ละส่วนผ่านขั้นตอนออกแบบแยกของมันเอง

## 4. สิ่งที่ถือว่าล้มเหลว (anti-goals)

- **คัดลอกโค้ด ชื่อ โลโก้ หรือหน้าตาของ Grok Bot** ห้ามนำไฟล์จากตัวติดตั้งที่แกะออกมามาใช้ ใช้ได้แค่เป็นข้อมูลอ้างอิงว่ามีฟีเจอร์อะไรบ้าง
- **Agent รันคำสั่งอันตรายโดยไม่ถามผู้ใช้** เมื่อไม่แน่ใจ (Jev ล่ม เน็ตหลุด ความมั่นใจต่ำ หรือคำตอบผิดรูปแบบ) ต้องถามผู้ใช้ทุกครั้ง
- **แอปค้างหรือใช้งานไม่ได้เพราะ Jev ใช้งานไม่ได้** แชตต้องใช้ได้ต่อ โดยให้ผู้ใช้เลือกตัวคุยเอง
- **เก็บ API key เป็นข้อความธรรมดา** ในไฟล์ตั้งค่าหรือในฐานข้อมูลแชต

## 5. ข้อจำกัด

- ภาษา: Rust
- แพลตฟอร์ม: Windows 11
- Jev ทำงานบนคลาวด์: ข้อความและคำสั่งที่ส่งให้ Jev ตัดสินจะออกนอกเครื่องไปที่ TypeSafe และมีค่าใช้จ่ายตาม token (ประมาณ $42 ต่อพันล้าน input token ตามหน้าเว็บ) ต้องแจ้งเรื่องนี้ผู้ใช้ในหน้าตั้งค่า

## 6. สิ่งที่ผู้ใช้ตัดสินใจแล้ว

- แอปเป็นของผู้ใช้เอง ไม่ได้ลอก Grok Bot
- ตัวคุยมี Hermes, Claude CLI และโมเดลผ่าน API key
- Jev ใช้ตัดสินใจเท่านั้น 2 เรื่อง คือเลือกตัวคุยและตรวจคำสั่งก่อนรัน

## 7. สิ่งที่ผู้ออกแบบ (Claude) ตัดสินใจเอง

ผู้ใช้ตรวจหรือเปลี่ยนรายการเหล่านี้ได้:

- **Framework: Tauri 2** หลังบ้านเป็น Rust หน้าจอเป็นเว็บ (เลือกเพราะ UI แชตแบบ streaming ทำบนเว็บง่ายกว่า egui/iced มาก)
- **Frontend**: เลือก framework ตามสะดวกของผู้สร้าง แต่ต้องไม่ลอกหน้าตา Grok Bot
- **ฐานข้อมูล**: SQLite (เช่น `rusqlite` หรือ `sqlx`) อยู่ในโฟลเดอร์ข้อมูลแอปของผู้ใช้
- **เก็บ API key**: Windows Credential Manager ผ่าน crate `keyring`
- **ผู้ใช้ปิดการเลือกตัวคุยอัตโนมัติได้** แล้วเลือกเองทุกครั้ง
- **รูปแบบ export**: Markdown และ JSON
- **เกณฑ์ความมั่นใจปรับได้ในหน้าตั้งค่า** ค่าเริ่มต้นดูในข้อ 9
- **เมื่อ Jev ใช้งานไม่ได้**: routing ให้ผู้ใช้เลือกเอง และตรวจคำสั่งให้ถามผู้ใช้ทุกครั้ง
- **API key ของ Jev**: เก็บใน Windows Credential Manager เหมือน key อื่น
- **คำสั่งที่ผู้ใช้แก้ไข**: ผู้ใช้แก้เองแล้วกดรัน ถือว่าผู้ใช้อนุมัติแล้ว จึงรันได้เลย แต่ยังส่งให้ Jev ตรวจเพื่อบันทึกผลไว้ในประวัติ
- **จำกัดรอบของ agent**: ข้อความเดียวรันคำสั่งต่อเนื่องได้ไม่เกิน 20 รอบ (ปรับในหน้าตั้งค่าได้) ครบแล้วต้องหยุดถามผู้ใช้

## 8. ตัวคุย (chat providers)

ทุกตัวต้องทำงานผ่าน trait เดียวกัน ให้หน้าแชตไม่ต้องรู้ว่ากำลังคุยกับตัวไหน แนวคิดคร่าว ๆ:

```rust
trait ChatProvider {
    fn id(&self) -> ProviderId;
    async fn stream(&self, conversation: &[Message]) -> Result<impl Stream<Item = ChatEvent>>;
}
// ChatEvent: TextDelta, ToolCallProposed { command }, Done, Error
```

### 8.1 Claude CLI
- เรียก `claude` ที่ติดตั้งไว้ในเครื่อง ในโหมดไม่โต้ตอบ รับผลเป็น stream JSON (`claude -p --output-format stream-json`; ผู้สร้างต้องตรวจ flag กับเวอร์ชันที่ติดตั้งอยู่จริง)
- ถ้าไม่เจอ `claude` ใน PATH ให้แสดงในหน้าตั้งค่าว่าใช้ไม่ได้ ไม่ทำให้แอปล้ม
- Claude CLI มีเครื่องมือรันคำสั่งของตัวเอง ห้ามเปิดให้มันรันคำสั่งบนเครื่องเองโดยไม่ผ่าน Jev (ดูข้อ 10)

### 8.2 โมเดลผ่าน API key
- ผู้ใช้ใส่ key และเลือกโมเดลในหน้าตั้งค่า
- v1 รองรับ Anthropic Messages API (ค่าเริ่มต้น `claude-opus-5-5`) ผู้สร้างจะทำ client ที่เข้ากับ OpenAI-compatible ไว้ด้วยก็ได้ แต่ไม่จำเป็น

### 8.3 Hermes Agent
ผู้ใช้ยืนยันว่า Hermes คือ **Hermes Agent** ของ Nous Research (https://github.com/nousresearch/hermes-agent) เป็นโปรแกรม agent ที่รันแยก (Python) รองรับ Windows แบบ native ผู้ใช้ติดตั้งเอง แอปเราไม่ติดตั้งให้

**วิธีเชื่อม**: ใช้ API server ในตัวของ Hermes (เอกสาร: `/docs/user-guide/features/api-server`)
- เปิดด้วย `API_SERVER_ENABLED=true` + `API_SERVER_KEY` ใน `~/.hermes/.env` แล้วรัน `hermes gateway` ค่าเริ่มต้นฟังที่ `http://127.0.0.1:8642/v1`
- Header `Authorization: Bearer <API_SERVER_KEY>` (เก็บ key ใน Credential Manager)
- ใช้ **Runs API**: `POST /v1/runs` (`input`, `session_id`) แล้วอ่าน SSE จาก `/v1/runs/{id}/events` (`message.delta`, `tool.started`, `tool.completed`, `approval.request`, `run.completed` และอื่น ๆ) หยุดด้วย `/v1/runs/{id}/stop`
- อนุมัติหรือปฏิเสธด้วย `POST /v1/runs/{id}/approval` body `{"request_id", "execution_generation", "choice": "once" | "deny"}`
- parser SSE ต้องข้ามบรรทัดที่ขึ้นต้นด้วย `:` (keepalive)
- แอปตรวจ `GET /health` ถ้าไม่ตอบ ให้แสดงในหน้าตั้งค่าว่า Hermes ใช้ไม่ได้ พร้อมวิธีเปิด

**การบังคับให้ทุกคำสั่งผ่าน Jev** (สำคัญที่สุดของส่วนนี้):
ระบบอนุมัติของ Hermes ส่ง `approval.request` เฉพาะคำสั่งที่ **มันเห็นว่าอันตราย** ส่วนคำสั่งอื่นรันเลย ระบบนี้อย่างเดียวจึงไม่พอสำหรับกฎ "ทุกคำสั่งผ่าน Jev" ทางที่เลือก (Claude ตัดสินใจเอง):
1. ปิด tool รันคำสั่งของ Hermes เอง (terminal, `execute_code` และ tool อื่นที่แตะ shell/ไฟล์) ผ่าน `hermes tools` / config
2. แอปเราเปิด **MCP server ในเครื่อง** ที่มี tool `run_command` ให้ Hermes ต่อเข้ามา (Hermes เป็น MCP client) ทุกการเรียก `run_command` ผ่านจุดตรวจของ Jev (ข้อ 9.2) แล้วรันด้วย agent ของเรา (ข้อ 10)
3. ถ้ายังมี `approval.request` เข้ามา (จาก tool ที่ปิดไม่หมด) ให้ส่ง Jev ตรวจเหมือนกัน แล้วตอบกลับ `once`/`deny`
4. เมื่อเริ่มแชต แอปตรวจ `GET /v1/toolsets` ถ้ายังเปิด tool รันคำสั่งของ Hermes อยู่ ให้เตือนผู้ใช้และไม่ส่งงานให้ Hermes จนกว่าจะแก้

ผู้สร้างต้องตรวจชื่อ tool/toolset และ key ใน config ที่แน่นอนจาก `/docs/reference/toolsets-reference` และ `/docs/user-guide/features/mcp`

แนวทาง MCP server เดียวกันนี้ใช้กับ Claude CLI ได้ด้วย (ปิด Bash tool ของ Claude แล้วให้ใช้ `run_command` ของเราแทน)

## 9. Jev: การตัดสินใจ

API (จาก docs.typesafe.ai):
- `POST https://api.typesafe.ai/v1/systemone`
- Header `Authorization: Bearer <key>` (env: `TYPESAFE_API_KEY`)
- Body: `{ "state": ..., "model": "jev-latest", "questions": { <id>: { "type": "choice" | "score" | "noul", "instructions": ..., "criteria": ... } } }`
- Response: `answers.<id>` ของ Choice มี `choice`, `probabilities` (รวมกันได้ 1) และ `confidence` (0 ถึง 1) ส่วน Noul มีแค่ `noul` (0 ถึง 1)
- docs ไม่ได้บอก rate limit และรูปแบบ error ผู้สร้างต้องตรวจจาก `https://docs.typesafe.ai/api` แล้วจัดการ error ทุกแบบด้วยการ fallback ตามข้อ 7

Rust SDK ไม่มี ให้เรียก HTTP เอง (เช่น `reqwest` + `serde`) แล้ว map คำตอบเป็นชนิดที่ชัดเจน

### 9.1 เลือกตัวคุย (routing)
- คำถามแบบ `choice` โดย `criteria` = ตัวคุยที่ **ใช้งานได้ตอนนั้น** (ตัวที่ยังไม่ตั้งค่าไม่ต้องใส่) แต่ละตัวมีคำอธิบายว่าเหมาะกับงานแบบไหน (คำอธิบายเริ่มต้นผู้สร้างเขียนเอง ผู้ใช้แก้ได้ในหน้าตั้งค่า)
- `state` = ข้อความล่าสุดของผู้ใช้ ส่วนประวัติแชตส่งเท่าที่จำเป็น (ผู้สร้างกำหนดเอง)
- ค่าเริ่มต้น: probability ของตัวที่เลือก ≥ 0.75 ส่งให้เลย ต่ำกว่านั้นให้ผู้ใช้เลือก โดยแสดงตัวเลือกที่ Jev เรียงลำดับความน่าจะเป็นมาให้
- แชตต้องแสดงว่าข้อความนี้ไปตัวไหน และ Jev มั่นใจแค่ไหน
- **ผู้ใช้ตัดสินใจ: สลับตัวคุยได้ทุกข้อความ** แชตเดียวอาจใช้หลายตัวปนกัน ผลที่ตามมา:
  - ประวัติแชตต้องเก็บในรูปแบบกลางที่ไม่ผูกกับตัวคุยตัวใด (ข้อความผู้ใช้ คำตอบ คำสั่งที่รัน และผลลัพธ์ พร้อมระบุว่าตัวไหนตอบ)
  - ทุกครั้งที่ส่งงาน แอปต้องแปลงประวัติทั้งแชตเป็นรูปแบบของตัวคุยตัวนั้น (Anthropic `messages`, Hermes `conversation_history`, และ prompt สำหรับ `claude -p`) ใช้ session ในตัวของ Claude CLI/Hermes ไม่ได้ เพราะมันจะไม่เห็นข้อความที่ตัวอื่นตอบ
  - ผลคำสั่งที่ตัวอื่นรันไว้ ให้ส่งเป็นข้อความบริบท ไม่ใช่ tool result ของตัวคุยปัจจุบัน
  - แชตยาวจะใช้ token มาก ผู้สร้างกำหนดวิธีตัดหรือย่อประวัติเองได้ แต่ต้องเก็บข้อความล่าสุดไว้ครบ

### 9.2 ตรวจคำสั่งก่อนรัน
- เมื่อตัวคุยเสนอคำสั่ง ส่งคำถามให้ Jev ในครั้งเดียว:
  - `is_safe` (noul): "คำสั่งนี้รันได้อย่างปลอดภัยโดยไม่ทำลายข้อมูล ไม่ส่งข้อมูลออกนอกเครื่อง และไม่เปลี่ยนการตั้งค่าระบบหรือไม่"
  - `risk` (choice): `read_only` / `modifies_files` / `destructive` / `network` / `system_change` / `other`
- ค่าเริ่มต้น: รันเองได้เฉพาะเมื่อ `is_safe ≥ 0.9` **และ** `risk == read_only` ที่ probability ≥ 0.9 นอกนั้นถามผู้ใช้ทุกครั้ง
- กล่องถามผู้ใช้ต้องแสดงคำสั่ง ไดเรกทอรีที่จะรัน และผลจาก Jev ให้ผู้ใช้เลือกรัน แก้คำสั่ง หรือปฏิเสธ
- ทุกคำสั่งที่รัน ทั้งที่รันเองและที่ผู้ใช้อนุมัติ ต้องบันทึกไว้ในประวัติแชตพร้อมผลการตัดสินของ Jev

## 10. Agent รันคำสั่ง

- คำสั่งจาก **ทุกตัวคุย** ต้องผ่านจุดตรวจเดียวกัน (ข้อ 9.2) ก่อนรัน
- รันใน working directory ที่ผู้ใช้เลือกต่อแชต
- มี timeout และปุ่มหยุดคำสั่ง ส่ง stdout/stderr กลับเข้าแชตแบบ streaming แล้วส่งผลให้ตัวคุยทำต่อได้
- Shell: PowerShell บน Windows (ผู้สร้างจะเพิ่มทางเลือกอื่นก็ได้)
- Claude CLI: ต้องตั้งค่าให้ **ไม่** รันเครื่องมือบนเครื่องเอง หรือดักคำขอรันมาผ่าน Jev ก่อน ผู้สร้างเลือกวิธีเอง แต่ต้องรับประกันว่าไม่มีคำสั่งใดหลุดจุดตรวจ

## 11. ประวัติแชตและ export

- เก็บแชต ข้อความ ตัวคุยที่ใช้ ผลการตัดสินของ Jev และคำสั่งที่รัน ไว้ใน SQLite
- รายการแชตด้านข้าง เปลี่ยนชื่อ ลบ และค้นหาได้ (การค้นหาแบบง่ายก็พอ)
- Export ทีละแชตเป็น Markdown หรือ JSON โดยใช้ dialog บันทึกไฟล์ของระบบ
- ต้องไม่มี API key อยู่ในไฟล์ export
